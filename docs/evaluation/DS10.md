# DS10: tamper cases with the fixed reader on whisky-v2-eval3

**Evidence label: LIVE (whisky-v2-eval3) for a1, a2 and c; INJECTED for b (gateway bytes) and for the decoy and future-revision cases (indexer API).** Protocol: [PROTOCOL.md](PROTOCOL.md) DS10. Raw files: [`docs/acceptance/2026-10-20-ds9-ds11/ds10/`](../acceptance/2026-10-20-ds9-ds11/ds10/).

**Status: closed with a stated limit (2026-10-21). The PROTOCOL.md DS10 pass criterion is not met** (section "Closed with a stated limit" below). a1, a2, c and b give the predeclared result in all three runs. The decoy and future-revision cases give it on Arbitrum Sepolia and Base Sepolia only; on Sepolia the browser's live read failed (below), in the run and in a retry, so those two cases have 2 of the required 3 runs. In no load did an expected-failure case show a fully verified display.

Public RPC nodes lagged their own receipts twice on Base Sepolia: the a1 record was rebuilt from the chain and the gateway after its mint (`adopted`), and the c revise was resumed on the token already minted (`resumed`), so no fixture was minted or pinned twice. The fixture file holds every transaction hash. 18 pins: a1 3, a2 3, c 9 (revision 0, decoy, revision 1), future 3.

**Deviation: the fixtures were made partly from uncommitted harness code.** `ds10-chain.cts` ran three times. The first invocation used the committed `2f8109e` (a1 on Arbitrum Sepolia; the a1 mint on Base Sepolia, whose record was lost to the RPC lag). The second used an uncommitted working copy with retrying reads and the a1 adopt path (a1 Base adopted, a1 Sepolia, a2 on all three chains, c on Arbitrum Sepolia, the c mint on Base Sepolia). The third used the copy committed unchanged afterwards in `2eef9b7` (c Base resumed, c Sepolia, the future envelopes). The second working copy was not committed as such. The fixtures are set-up transactions and are verified independently: the reader and the harness verifier read their records from the chain and the gateway. The DS10 observations are the reader loads, which ran from `5db5cd7`, whose tree state was not recorded in a file.

The reader ran in headless Chromium against the production build with `NEXT_PUBLIC_INDEXER_URL` set to the stand-in ([`ds10-standin.mjs`](../acceptance/automation/eval3/ds10-standin.mjs)), which forwards everything to the real indexer and rewrites only the decoy (switched on for that case alone) and future summaries ([`ds10-ui.mjs`](../acceptance/automation/eval3/ds10-ui.mjs)). Nothing was signed or sent. The harness verifier's results at fixture time agree with the reader for a1, a2 and c on every chain.

## Why the Sepolia loads lack a live read

The web app's browser transport is viem's default `http()` for each chain; for Sepolia that is `https://11155111.rpc.thirdweb.com`. Every Sepolia page dump names it as the failing request (`HTTP request failed. URL: https://11155111.rpc.thirdweb.com/`, [`pages/`](../acceptance/2026-10-20-ds9-ds11/ds10/pages/)). A filed probe of 2026-10-20 17:24 UTC ([`rpc-probe-2026-10-20T1724Z.txt`](../acceptance/2026-10-20-ds9-ds11/ds10/rpc-probe-2026-10-20T1724Z.txt), [`rpc-probe.sh`](../acceptance/automation/eval3/rpc-probe.sh)) got HTTP 200 for the first `eth_blockNumber` and 429 for the next four, two seconds apart; the Arbitrum and Base Sepolia defaults answered all five. The endpoint answers occasionally (the a1 Sepolia load of the run got its receipt read), but not the burst a passport page makes.

A retry of the Sepolia loads on the same app and stand-in, from `c5b08e9` (the retry script printed a clean tree; not recorded in a file), at 17:27 to 17:29 UTC after quiet periods of 90 and 60 s, gave the same "live read failed" fallback for a1, a2, c, decoy and future ([`sepolia-retry/`](../acceptance/2026-10-20-ds9-ds11/ds10/sepolia-retry/); b was not repeated); a1, a2 and c again failed their named check, decoy and future again did not reach their predeclared result. The retry's `ds10-standin-hits.json` also holds the hits of the first run (16:46 to 16:49 UTC), because the stand-in process kept running; the retry's entries start at 17:27 UTC.

This is an availability limit of the demonstrator's Sepolia read path, not a reader fault. Of the seven Sepolia loads (a1, a2, c, b control and altered, decoy, future), only the decoy and future-revision loads fall short.

## Closed with a stated limit (2026-10-21)

The dataset is closed without repeating the two Sepolia loads.

- **What stays short.** Decoy and future revision on Sepolia: n = 2 of 3 for each of these two cases (Arbitrum Sepolia and Base Sepolia met; the Sepolia load did not reach its predeclared result). Every other case meets its result on all three chains (n = 3).
- **Cause.** The browser's default Sepolia RPC (`https://11155111.rpc.thirdweb.com`, viem `http()`) answered HTTP 429 to the burst of requests a passport page makes, so the reader had no live read and fell back to indexer-only results. An availability limit of the app's read path, not a reader fault.
- **Dated attempts.** 2026-10-20 16:46 to 16:49 UTC (the run) and 2026-10-20 17:27 to 17:29 UTC (the Sepolia retry from `c5b08e9`, [`sepolia-retry/`](../acceptance/2026-10-20-ds9-ds11/ds10/sepolia-retry/)); both gave "live read failed" for the Sepolia decoy and future loads. Probe of the endpoint: 2026-10-20 17:24 UTC (first request 200, the next four 429).
- **Why no third attempt.** No record gives an exact repeatable command for these loads: they need the app built with `NEXT_PUBLIC_INDEXER_URL` pointing at the stand-in, a synced local indexer and the stand-in process (the script headers name the parts, `ONLY_CHAIN=sep` in [`ds10-ui.mjs`](../acceptance/automation/eval3/ds10-ui.mjs)), and that environment was not set up again.
- **What the result supports.** In every load, including the two short Sepolia loads, no expected-failure case showed a fully verified display; the decoy and future-revision detection is shown on two of the three chains.

## Limits

- Cases b, decoy and future are INJECTED at their boundary (gateway response, indexer API); they show what the reader does with such input, not that a real gateway or the real indexer produced it.
- n = 3 per case means three tokens on three chains, one load each; it is not a failure-rate estimate.
