# Evaluation protocol

This file states what each dataset measures, how, how many times, and what counts as a pass. Each dataset's rules were committed before its run. A negative outcome is reported as the result. Nothing here is a measurement; numbers in it are acceptance thresholds or limits of a run.

Scope: the datasets collected on the deployment generation `whisky-v2-eval3` (DS1 to DS4 and DS9 to DS12) and the local storage baseline DS5. Dataset numbers missing from this sequence are not part of this evidence.

## 1. Rules for every dataset

1. **Generation.** Every live dataset runs against one deployed generation, `whisky-v2-eval3`: Sepolia (chain id 11155111, LayerZero eid 40161), Arbitrum Sepolia (421614 / 40231) and Base Sepolia (84532 / 40245). The run header names it. Runs of other generations are never pooled with it. A 10/10 smoke run over all six directions precedes the datasets. A redeploy after the first live dataset run restarts all live datasets.
2. **Clocks.** Never pool values from different clocks.
   - *Cross-chain delivery, primary clock:* block timestamp of the source `ONFTSent` to block timestamp of the destination `ONFTReceived`. Removes the polling overshoot (5 s poll interval in the harness).
   - *Cross-chain delivery, continuity clock:* source block timestamp to the first successful destination poll. Recorded beside the primary clock, labelled, never merged with it.
   - *Same-chain time:* submission to first receipt (wall clock of the harness), with the block-timestamp difference beside it.
   - *UI claims:* the app panel clock, used only for DS12.
   - Chain clocks can differ by seconds; clock skew between chains is not measured, and the text says so.
3. **Observation.** One operation on the deployed code whose receipt is kept. A failed or timed-out operation is an observation of failure, counted, not dropped. The delivery timeout is 1,800 s; a hop can end earlier on LayerZero Scan's record of the send (section 1.1).
4. **Windows.** A window is one run. Its label is an identifier (DS2 uses w1, w2 and w3); its actual UTC start is recorded in the header. A dataset names how many runs it takes (DS2: three). Report each window and the pool; pooling across windows is allowed. DS2 starts are at least three hours apart. There is no calendar-day requirement; the write-up states the actual observation dates and that results describe those conditions only.
5. **Statistics.** Median, quartiles, p95, minimum, maximum and the count of outliers (outliers are reported, never removed). Confidence intervals only from n ≥ 10. Below n = 10 only raw values are printed. A table caption names n, the clock, the window and the evidence label.
6. **Cost.** Receipt gas fee = `gasUsed × effectiveGasPrice`. The LayerZero fee is the `msg.value` of the send. Report gas units and native amounts always. Any USD figure is a labelled, dated, hypothetical mainnet conversion from one named price source and is never a measurement. On Base the receipt gas fee excludes the separate L1 data charge and is not the complete transaction cost (section 1.2).
7. **Run header.** Each report records: git SHA and dirty flag, deployment id, deployed bytecode hash per chain, RPC provider class (public or keyed), tool versions (node, hardhat, forge, ethers), window label, and every parameter of the run. The raw JSON is committed next to the generated Markdown and LaTeX.
8. **Inventory.** Every run appends its token ids to the fixture ledger (`smart_contracts/fixtures/ledger.md`: token id, chain, purpose, run id). The run id is written into each payload's `description`. Fixtures are never counted as real passports.
9. **Raw data first.** Every reported number comes from a committed raw file, and every table is generated from it (`e2e:tables`). Regeneration must give an empty diff.
10. **Pins.** A CID cited by a `whisky-v2-eval3` run is never unpinned.
11. **Fee policy.** The harness asks for a priority fee of 0.001 gwei (`tasks/fees.ts`), raised where a chain has a minimum price, instead of ethers' default of 1.5 gwei. The tip is `max(0.001 gwei, eth_gasPrice - base fee)` and the ceiling twice the base fee plus the tip; the run header records the formula (`feePolicy`) and the floor (`priorityFeeFloorWei`), and each step records its `effectiveGasPrice`. A report that used another policy is not pooled with these. The policy says nothing about timing under congestion, and a fee fixed at submission can become too low before inclusion: a step that has waited ten minutes for its receipt then fails with that cause (`waitReceipt` times out), so the run reports it instead of hanging. The timeout does not cancel the transaction: it can still be mined later, and for a `send` the LayerZero fee is then paid and the token moves unrecorded. The flow's error and a step named `submitted, no receipt seen` carry the transaction hash; it is checked on the chain and the token id entered in the ledger before the run is repeated, and later steps of that account queue behind its nonce. Same-chain times may run slower than a wallet with default fees during congestion.

### 1.1 LayerZero Scan preflight and early stop

LayerZero Scan's API (`scan-testnet.layerzero-api.com/v1`) is the primary source on whether LayerZero is handling this application's messages and on where a hop stands. Delivery itself is observed on the destination chain (`ownerOf` and `ONFTReceived`). The rules are stop criteria on Scan's view, not proof of what LayerZero did (`tasks/lz-scan.ts`). Every live task runs under `scripts/live.sh`, with `scripts/scan-health.sh` green before a send.

- **Preflight.** A run that sends first checks every pathway it will send on. For each pathway it reads the source endpoint's `outboundNonce` for this application and Scan's newest message on the pathway (`/messages/pathway/<srcEid>-<dstEid>-<sender>-<receiver>`). The run does not start, and sends nothing, if the endpoint has sent a nonce Scan does not have, or if Scan's newest message on the pathway is in a terminal status or not delivered 15 minutes after it was sent. A pathway with no send yet decides nothing. If Scan does not answer, the run refuses to start unless `--allow-unknown-scan` is given, which the header records. Scan's 25 newest messages from each source chain, of any application, are recorded beside the verdicts but decide nothing. Verdicts and traffic go into the run header (`scanPreflight`).
- **No record after 5 minutes.** Scan's record of a send is read every minute while the hop waits. If Scan still has no record 5 minutes after the send, the destination is read once more. If the token is still not there, the hop is a counted failure and the run starts no further flow that sends. This takes the send as not picked up by LayerZero, which Scan's silence suggests but does not prove; the report says "no record on LayerZero Scan".
- **Stuck after 15 minutes.** A send that Scan knows but has not delivered 15 minutes after it is handled in the same way: one more read of the destination, then a counted failure, and the run starts no further sending flow.
- **Terminal status.** If Scan reports FAILED, BLOCKED, PAYLOAD_STORED, APPLICATION_BURNED or APPLICATION_SKIPPED, the hop ends at once as a counted failure; the run goes on with the next pair, as the DS2 stop rule says.
- **Scan errors.** A rate limit, a 5xx or an unreachable Scan is not taken as no record, and a Scan request is given up after 15 s. Three consecutive Scan HTTP or network errors after the five-minute no-record grace stop the run after a final destination read; Scan unavailability is not evidence that LayerZero failed.
- **Interruption.** SIGINT and SIGTERM write a checkpoint labelled `status: "interrupted"`; paid sends and pending transaction hashes stay in the report.

The report of a run that stops gives every planned direction a row, with nothing sent where no hop was made, so the shortfall is counted. A slow but healthy delivery after one of these limits is counted as a failure, so the delivery-time distribution is censored at the limit that applied, and the write-up says so if it happens. When an RPC refuses a long `eth_getLogs` range, the lookup of `ONFTReceived` drops to 100-block ranges.

### 1.2 Base fee components

The `feeWei = gasUsed × effectiveGasPrice` metric is called the receipt gas fee; on Base it excludes the separate L1 data charge and must not be described as the complete transaction cost ([Base fee specification](https://docs.base.org/specifications/transactions/network-fees)). Transaction steps may also carry an optional `l1FeeWei` decimal string from a raw Base receipt matching both the transaction hash and its sealed, nonzero block hash. Base may return a preconfirmation receipt with an all-zero block hash. After preserving its first-observation timestamp, the harness refreshes the same transaction for at most 15 seconds until a sealed receipt is available; status, logs, gas, price and block identity then come consistently from that receipt. If sealing is unavailable, the failed step files the initial receipt as diagnostic-only `provisionalReceipt` without measured gas, fee or block fields. The same-chain receipt-observation time may therefore include Base preconfirmation and does not measure finality. Block lookup by hash, then height with strict hash matching, has a separate 15-second budget. The supplementary L1 read starts after the first-receipt timestamp, has a five-second bound and cannot fail a confirmed transaction; unavailable, malformed or mismatched data stay absent, while an explicitly reported zero stays zero. Tables use the receipt gas fee; the LayerZero fee paid as `msg.value` remains separate. A [reported Base preconfirmation fee issue](https://github.com/base/base/issues/5473) is the reason a sealed receipt is required for the supplementary L1 value; that report is not a measurement of these transactions.

## 2. Evidence labels

LOCAL (Foundry or Hardhat, no live chain), `LIVE (<generation>)` (the named deployment generation, here LIVE (whisky-v2-eval3)), INJECTED (a fault inserted at a boundary, such as altered bytes at the browser or a served decoy at the indexer), MANUAL (done by hand against a checklist).

## 3. Datasets

For each: the question, parameters and n, the clock, the pass criterion, the stop rule and the label. "Stop rule" says when a run is abandoned and what is filed.

### DS1: single operations on one chain

- **Question.** What do confirmation time and gas cost for each operation on each chain, including a Sepolia `mint`?
- **Parameters.** `mint` by the issuer to its own account, `revise` at revision depth 1 to 10 on the first of those tokens, same-chain `transferFrom` by the holder to a fresh address. n ≥ 10 per operation and chain, three chains. 20 real pins per chain. The first mint per chain also creates the harness account's balance slot and is reported apart; the cost of a new holder's balance slot is taken from the holder's `transferFrom` to a fresh address.
- **Clock.** Same-chain time (rule 2).
- **Pass.** At least 10 successful observations for every operation × chain cell (revise: depths 1 to 10 each covered at least once, 10 observations in total per chain); every observation carries gas used, effective gas price, fee in wei, block number and both same-chain times; the gas table has a Sepolia `mint` row. A cell below 10 is reported as not met with its count, not padded. Unexpected reverts are counted and filed with their transaction hash.
- **Stop.** Faucet balance below one further operation's quoted cost, or three consecutive RPC failures on one chain: stop that chain, file what exists, mark the rest not collected.
- **Label.** LIVE (whisky-v2-eval3).

### DS2: cross-chain delivery, send gas and fee

- **Question.** How long does a `send` take to arrive and what does it cost, per direction?
- **Parameters.** Three windows of `e2e:latency --hops 8` per pair: 12 sends per direction (four per window), 72 in total, nine pins. A per-window summary has n = 4 and shows raw values; the observations of one window are four back-to-back hops of one token, so the pooled interval is optimistic and the write-up says so. The first hop of each window is reported. Both delivery clocks recorded. Failures and timeouts counted.
- **Clock.** Primary and continuity clocks (rule 2), reported in separate columns.
- **Pass.** 12 sends per direction over three windows (four per window), each delivered or counted as a failure, and the shortfall against 12 recorded with the cause; a direction under n = 10 after the three windows is completed with extra windows (see Stop). Each delivered hop has both delivery clocks, the quoted LayerZero fee, the paid `msg.value` and the source transaction fee. Per-window and pooled summaries are generated, with intervals only where n ≥ 10 in that cell.
- **Stop.** A hop that is not delivered after the timeout is a counted failure and strands the token, which ends that pair's window; two consecutive failures on one pathway stop that pathway. A direction whose pooled n is under 10 is then owed an extra window, reported as a data-dependent extension of n, with the failed window beside it and not instead of it. The stuck message is not recovered inside DS2 and its token id is entered in the ledger.
- **Label.** LIVE (whisky-v2-eval3).

### DS3: edge cases on chain

- **Question.** Do the authorisation and input rules hold on the live chains, and how much receive-gas headroom does the maximum-length CID leave?
- **Parameters.** Each case once per chain, n = 1. The rules are deterministic and every chain runs the same compiled source (the runtime differs only in the immutable `idPrefix` and endpoint). A 96-byte CID delivered to each destination, sent from the cheapest other chain under the fee quotes taken at deployment (Arbitrum to Base and Sepolia, Base to Arbitrum; enforced gas 286,000 into each L2 and 1,291,000 into Sepolia); `mint` by a non-issuer and `revise` by the holder (`NotIssuer`, mined); approved-operator `transferFrom`, after which the new holder's `revise` reverts `NotIssuer` (`eth_call`); non-owner `setIssuer`, `setPeer`, `setEnforcedOptions`, `setBaseURI` and a direct `lzReceive` (`eth_call`); a broadcast replay of a delivered packet; `UnexpectedTokenId` and `StaleRevision` on all chains. The attempt to import an own-namespace id (S1) is a LOCAL result (a forged message needs a hostile peer) and is cited from the Foundry suite.
- **Clock.** None for the authorisation cases; the 96-byte CID case records the primary delivery clock and the destination gas used.
- **Pass.** For each case one observation per chain, with a receipt for a broadcast case and a recorded `eth_call` revert for the others: a rejection case reverts with the named custom error (decoded from the ABI: `NotIssuer`, `OwnableUnauthorizedAccount`, `OnlyEndpoint`, `UnexpectedTokenId`, `StaleRevision`, `ERC721InsufficientApproval`), a permitted case succeeds. The 96-byte CID is delivered to each destination with the destination gas used recorded against the enforced gas, or the failure is filed with its transaction and the recovery by `lzReceive` at higher gas (permissionless) is filed as a result. A replay of a delivered packet must fail; a replay that succeeds is a finding that stops the dataset.
- **Stop.** A 96-byte CID delivery that sticks: stop that destination, recover it, use a fresh token for the remaining cases.
- **Label.** LIVE (whisky-v2-eval3); LOCAL for the S1 import case.

### DS4: minimal scale confirmation

- **Question.** At small scale, do pipelined ERC-721 mints retain the DS1 per-token gas cost, and do back-to-back sends retain the DS2 per-send cost and overlap in delivery time?
- **Parameters.** One run on `whisky-v2-eval3`: 20 issuer mints to the harness account on Base Sepolia (84532 / eid 40245), then 10 of those tokens sent Base Sepolia to Arbitrum Sepolia (40245 to 40231). Prepare consecutive explicit nonces, gas limits and fee policy before each broadcast loop; broadcast without awaiting receipts, then await receipts in parallel. Estimate the first state-valid mint once and give every mint a 25% gas margin; estimate each independent send with its own fee quote and give it a 25% gas margin. Each canonical cask envelope has the run id in its description; compute and cache its CIDv1 locally, assert its length is 59 bytes, and pin nothing. Keep every submitted hash. Record each transaction's nonce, gas, receipt fee (and Base L1 fee), block, submission and receipt times, and both same-chain clocks. Record quoted and paid native fee, Scan status, destination receipt and verification for each send. The batch records first submission to last receipt, first to last inclusion block timestamp, distinct inclusion blocks and the largest number in one block; for sends it also records first `ONFTSent` to last `ONFTReceived` and its continuity counterpart. No larger inventory is measured.
- **Clock.** Same-chain, primary delivery and continuity clocks of rule 2, kept separate. The primary batch delivery clock ends at the last destination `ONFTReceived` block timestamp; the continuity clock ends at the last successful destination poll. Chain clock skew is unmeasured. Observations from one account are dependent; intervals are optimistic and the write-up says so. For n = 20 and n = 10, report median, quartiles, p95, min, max, outliers and intervals (rule 5).
- **Pass.** Every mint mined with status 1 and gasUsed within 148,081–163,667 (±5% of DS1 Base Sepolia later mint to self median 155,874). Every send mined with status 1 and source gasUsed within 222,805–246,257 (±5% of DS2 L2 source send gas 234,531; sends are absent from DS1). Every paid `msg.value` within 0.000103049319325419–0.000113896616096515 ETH (±5% of DS2 Base to Arbitrum's single paid value 0.000108472967710967 ETH). DS2 measured a single paid fee on every Base-to-Arbitrum send, so this band is set before the run, not a range measured by DS2; LayerZero's quote depends on destination gas and price feeds, so a fee outside the band is plausible and is filed as the result. Report receipt gas fees beside this comparison without a pass threshold. All 10 sends must be delivered with complete primary clocks; report how many individual clocks are in DS2's Base to Arbitrum range 26–52 s, but judge the time to the last delivery (the batch primary clock) against that range. Every mint and delivered token has verified content, binding and history, and the expected on-chain history hash. Report mint batch time against the sequential derivation (20 × DS1 Base mint block-difference median of 2 s, from `ops-1792442510606.json`) and blocks spanned, without a pass threshold. A miss is the result, never grounds for a rerun.
- **Stop.** Scan preflight for Base to Arbitrum and `scripts/scan-health.sh` must pass; Base balance must be at least twice the quoted batch cost before broadcasting. If a mint reverts or has no sealed receipt, send nothing; retain the nonce gap and all available observations. For each delivery apply the Scan rules of section 1.1 (no record after 5 minutes, stuck after 15 minutes, terminal status, and the 1,800 s timeout, with the final destination read and the Scan error distinction). Such a hop is a counted failure. Start no further sends after a stop; all ten may already have been broadcast. SIGINT/SIGTERM writes a checkpoint with every in-flight hash.
- **Label.** LIVE (whisky-v2-eval3). The ledger has 20 rows (`DS4 mint` or `DS4 mint, send to arbitrum-sepolia`). The unpinned CIDs have no gateway-served payload; verification uses the cached local bytes and the write-up states this limit.

### DS5: storage baseline

- **Question.** What does it cost to store the payload on chain as `bytes` against storing `(revision, cid)`? This is the comparison behind "efficiently" in the hypothesis and the storage-cost challenge.
- **Parameters.** Payload sizes: the 312-byte shared vector, a real cask, a real bottle with 1, 3 and 10 `sourceCasks`, 2 KiB, 64 KiB (the cap). Growth over 1, 5 and 20 revisions. Real payload bytes from the fixture set (calldata cost depends on zero bytes). Foundry with forge 1.8.5 and `--isolate` for cold-storage figures. The registry side counts the history-hash slot.
- **Clock.** None (gas units).
- **Pass.** The report gives, per size and revision count, gas for storing the bytes on chain, gas for `(revision, cid)`, and their ratio; the table regenerates identically with forge 1.8.5. The ratio is reported whichever way it falls.
- **Stop.** None; the run is local.
- **Label.** LOCAL.

### DS9: retrieval and redundancy

- **Question.** Does a second copy, held without Pinata, serve every cited payload so that it still verifies against its CID (storage redundancy)?
- **Parameters.** The ten CIDs of `whisky-v2-eval3`, fixed before the run and written into the report header: the current CID (`passportOf`) of tokens taken by id from the fixture ledger, one DS1 token per chain (3), the DS2 token of each pair after its last hop (3), one DS10 token, the DS11 bottle and two DS12 tokens. A local IPFS node (kubo) pins each one from the network (`ipfs pin add`, daemon online); if the network fetch fails, the bytes fetched through the Pinata gateway are added (`ipfs add --cid-version 1 --raw-leaves`) and must give the same CID, and the report says which way each copy was made. Each CID is then read once through the Pinata gateway and once from the local node with the daemon stopped (`ipfs --offline cat <cid>`), so the second read uses only the local copy. No public gateway, second provider, windows or unpin test.
- **Clock.** None; the result is verified or not, per CID and path.
- **Pass.** Every listed CID verifies through both paths. A failure is reported as the result.
- **Label.** LIVE (whisky-v2-eval3) for the gateway path; LOCAL for the node path.

### DS10: tamper cases with the fixed reader

- **Question.** Does the reader detect each tamper case, with n ≥ 3 each?
- **Parameters.** a1, a2, c, b, decoy predecessor, future revision, on different tokens and chains.
- **Pass.** In each of six cases, all n ≥ 3 runs give the predeclared result. a1/a2/c/b fail their named content, binding or history check. Future-revision injection gives binding: unconfirmed above the live tip and the exact banner “The chain holds revision M; the indexer lists revision N. Revisions above M are not confirmed on chain.” The decoy gives history hash: failed and recorded on chain: failed, even if its payload links are consistent. A fully verified display in an expected-failure case is a reader failure and is retained.
- **Injection boundary.** A local indexer stand-in serves decoy and future-revision summaries through the indexer API; these cases are INJECTED at that boundary, not a claim that the real indexer emitted them. Payload-byte injection remains case b. Expected UI strings and assurance rules are those of the reader's verification results ([technical reference](../TECHNICAL-REFERENCE.md#verification-results)).
- **Stop.** None.
- **Label.** LIVE (whisky-v2-eval3); INJECTED for case b and for the dishonest-indexer cases.

### DS11: bottle from casks

- **Question.** Does the bottle lifecycle work with validated `sourceCasks`?
- **Parameters.** Two casks; a bottle with one and one with two or more `sourceCasks`; revise; send; read on the destination. Rejection cases: a missing cask, a non-cask, a nonexistent revision.
- **Pass.** Each accepted bottle (one `sourceCask`, two or more) is read on the destination with `content`, `binding`, `history` and "recorded on chain" all verified; each of the three rejection cases is refused with its expected message and no transaction is sent.
- **Label.** LIVE (whisky-v2-eval3); LOCAL for rejections.

### DS12: current UI

- **Question.** Do the user stories work in the current UI, and how long do they take?
- **Parameters.** Live Playwright and indexer suites once; click-to-confirmed and confirmed-to-verified, n ≥ 10 per operation; screenshots for the figures.
- **Clock and raw file.** The recorder writes `app/apps/web/e2e-live/out/ui-timings-<startedAt>.json` (or `UI_TIMINGS_OUT`); a copy is filed as `docs/acceptance/<date>-live-suite/ui-timings.json`. The header carries start, commit/dirty state, deployment/chains, Node/Playwright versions and indexer URL. Each attempted mint/revise/send has token, chain, direction where applicable, transaction hash when known, clickAt, confirmedAt, verifiedAt, outcome and optional delivery milestones/last reader state. Unconfirmed attempts retain confirmedAt null; a mint before identity allocation uses tokenId pending. Outcomes are verified, timed-out and not-measured; timeouts and failures are retained, never dropped.
- **Resolution.** Click/confirmation/verification observations use the Playwright process clock; panel mounted/delivered/indexer-observed attributes use the browser clock on the same machine. Panel mount follows the source receipt. Destination and indexer milestones latch independently at first observation; indexer polling continues for at most 60 seconds after ownership delivery. The panel polls every 6 s; settled stale reader pages reload every 5 s, with pending verification observed every 200 ms instead of being repeatedly aborted. Reader and panel deadlines run concurrently. Captions state these resolutions; the panel is an observation clock, not a block timestamp.
- **Repetitions and shortfall.** Build with INDEXER_URL to measure confirmed-to-verified against live reads; otherwise verifiedAt is null with not-measured outcome and the shortfall is stated. LIVE_REPEAT=n (default 1) makes n mint/revise pairs, one extra stale-probe revision, and n round trips (2n sends, n per direction) with the final token. LIVE_REPEAT=10 therefore meets n ≥ 10 per action and send direction in one invocation.
- **Pass.** Every live suite is run once and its result filed (green, or each failure with its cause); click-to-confirmed and confirmed-to-verified written to JSON with n ≥ 10 per operation, or the shortfall stated.
- **Label.** LIVE (whisky-v2-eval3).

## 4. Fixed inputs

The fixture set (cask minimal and full; bottle with 1, 3 and 10 `sourceCasks`; `granularity: batch` with a quantity; revision chains of depth 1, 5, 10 and 20; the hostile set; a 96-byte CID string) is built by the harness (`smart_contracts/tasks/fixtures.ts`), committed under `smart_contracts/fixtures/` with a sizes file, and read by the Foundry and app tests. The app receives a copy with a drift check; no subproject imports another.
